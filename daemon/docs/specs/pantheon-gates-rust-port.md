## Frame

**Strategic weight.** This is the foundation of the Pantheon validation story, which underpins the Old Iron commercial thesis. Not exploratory infrastructure. Commercial revenue is distant; the foundation is not. Delivery is **ASAP, work continuously until Gate 0 passes end-to-end.**

**Definition of done for v1.** `pantheon-gates` runs Pantheon's Gate 0 (four sub-gates 0.1 / 0.2 / 0.3 / 0.4 per REQ-059) end-to-end, with the Triumvirate daemon and real downstream services at each stage, producing valid PASS verdicts and complete evidence bundles for each sub-gate. No time-box; work until the condition is met.

**Why these gates exist — three purposes.** The gates are not JUST validation tests. They simultaneously serve:

1. **Validation** — "does Pantheon currently handle workload X at scale Y?" Pass/fail.
2. **Requirements forcing-function** — each gate defines a capability that MUST exist before it's passable. Gate 5 (Full Trinity) cannot pass without three-role concurrent orchestration; Gate 7 (soak/stress) cannot pass without survivability under sustained load. The gates are an **executable requirements doc** for what Pantheon must become.
3. **Commercial readiness proof** — a passed gate corresponds to a class of engagement complexity. "Gate 5 passed on date X with evidence bundle Y" is the defensible claim handed to an Old Iron (or equivalent) client asking "can your swarm handle a 500K-line COBOL modernization?"

**pantheon-gates is the infrastructure-readiness story (System A).** It does not judge output quality (that's System B, a sibling spec) or select winners among candidate outputs (that's System C, another sibling). All three systems must exist for a full commercial Pantheon story; pantheon-gates is the first, because the other two depend on its evidence-bundle + run infrastructure.

**No mocks.** No synthetic bootstrap generators. No "fake backend to unblock later work." Every Backend impl talks to a real process serving a real model. vLLM on homebox or GCE, MLX-lm on Mac, daemon-http on the Triumvirate daemon, Anthropic/OpenAI via real keys — all real.

**Abstraction stance.** A fleet of 1 is a fleet of 1. No special case. The Backend trait and FleetOrchestrator trait let Gate 0 (one endpoint) and Gate 5 (three-role fleet) use the same surface from day one.

| **REQ-052** | **Redaction pass at record-write time — regex + field-name + structural.** Before serializing any artifact to the bundle (prompt records, manifest, metrics, logs, preflight outputs), runner applies a layered redaction strategy: **(a) Regex over string values** matching hardcoded v1 pattern list — OpenAI general (`sk-[A-Za-z0-9]{20,}` covers both legacy `sk-` and current `sk-proj-` prefix variants), Anthropic (`sk-ant-[A-Za-z0-9\-_]+` covers `sk-ant-api03-` and `sk-ant-oat01-`), Google API keys (`AIza[0-9A-Za-z\-_]{35}`), AWS access keys (`AKIA[A-Z0-9]{16}`), Slack tokens (`xox[abprs]-[A-Za-z0-9\-]+`), JWT three-segment (`[A-Za-z0-9\-_]+\.[A-Za-z0-9\-_]+\.[A-Za-z0-9\-_.+/=]+`), Bearer headers (`Bearer\s+[A-Za-z0-9\._\-]+`), URLs with embedded basic-auth creds (`https?://[^:]+:[^@]+@`), SSH/PGP private-key block markers (`-----BEGIN (RSA |DSA |EC |OPENSSH |PGP )?PRIVATE KEY(\s+BLOCK)?-----`), Google service-account JSON private-key marker (the literal `"private_key":` string when found adjacent to BEGIN PRIVATE KEY). **(b) Field-name redaction for JSON/YAML structured data** — any object field whose key matches case-insensitive regex `(api[_\-]?key|auth[_\-]?token|bearer|authorization|credential|password|secret|private[_\-]?key|session[_\-]?token|refresh[_\-]?token)$` has its scalar value replaced with `[REDACTED:field_name]` regardless of content. Catches credentials in structured contexts (daemon health dumps, config echoes, tool argument captures) where the value isn't recognizably key-shaped but the field name reveals intent. **(c) Structural preservation** — redaction replaces content but preserves JSON/JSONL schema (the redacted value is always a string `[REDACTED:<category>]`, keeping the record parseable for downstream consumers). **(d) Deterministic tokenization for correlation** — when the same raw credential value appears multiple times across a bundle's records, redaction assigns a stable suffix (`[REDACTED:api_key:A]`, `[REDACTED:api_key:B]`) so investigators can see "this same credential was used in requests X, Y, Z" without knowing what it is. Hash for stability: `sha256(raw_value)[..8]` mapped to letter suffixes. Redaction is applied once at write; downstream consumers see redacted data. NO runtime configuration of the regex or field-name lists in v1 (keeps the baseline consistent); v2 adds project-level extensions AND the "Dual-Artifact" pattern — public redacted bundle + WORM-archive vaulted forensic bundle for enterprise/compliance deployments (Old Iron path). A redaction counter per category + field-name + per-tokenization-bucket is included in `manifest.json` for audit. **Known false-positive mitigation:** field-name redaction trumps regex redaction when both fire on the same value (avoids double-redaction labels); minified-identifier collisions (base64-looking SHA hashes, minified JS symbols) are intentionally left unredacted because over-redaction in technical logs destroys debugging utility — the field-name layer catches the high-value false-negative cases that loose regex would miss anyway |
| **REQ-053** | **First-run-is-baseline pattern (D-12 lock).** No separate "reference-run tool." The first K successful Gate N runs (per REQ-054) collectively capture the baseline; subsequent Gate N runs verdict against it. This matches the 2026 industry-standard Helicone/Arize "Primary Capture" protocol. No chicken-and-egg, no separate code path — the same `pantheon-gates gate run --gate N` command bootstraps its own baseline on first invocation and uses that baseline on every subsequent invocation |
| **REQ-054** | **Baseline cluster K=5 × num_tasks=20 default.** Gate YAML may override `baseline_cluster_size: K` (default 5). First K successful runs of the gate (each of which produces raw metrics per scenario) aggregate into the baseline bundle at `~/.pantheon/evidence/baseline/gate-{N}/{fingerprint-hash}/`. Aggregation: median of per-run medians, p95 of per-run p95s, p99 of per-run p99s, plus std-dev across the K runs for each metric. Total prompts across cluster should be ≥100 for statistical validity — if a gate's per-run `num_tasks × K < 100`, runner emits a WARN at first-run noting the cluster is below the research-recommended threshold |
| **REQ-055** | **Sanity targets — absolute, pre-baseline.** Every gate YAML has a `sanity_targets:` block evaluated against ABSOLUTE criteria (no formula references). Purpose: catch "baseline captured against broken infra." First-run evaluates ONLY sanity_targets (performance_targets SKIPPED because no baseline exists yet). Subsequent runs evaluate both. Any run failing sanity is EXCLUDED from the baseline cluster AND receives its own FAIL verdict. Default sanity checks (always on, cannot be removed): `tasks_errored == 0`, `all_responses_non_empty == true`, `min_completion_tokens ≥ 10`, `usage_reports_present_count == successful_ops`. Gate YAML can add sanity targets; can't weaken defaults |
| **REQ-056** | **Formula-based performance_targets.** Gate YAML `performance_targets:` block may use formula syntax referencing the baseline: `round_trip_median_ms: { max: "baseline.round_trip_median_ms * 1.5" }`, `p99_latency_ms: { max: "baseline.p99_latency_ms * 1.3" }`. At gate-load time, runner resolves formulas against the stored baseline's metric values. Formula parser supports: arithmetic (+/-/*/÷), single variable reference (`baseline.<metric>`), numeric literals. Parentheses allowed. Division-by-zero = CONFIG_ERROR. When NO baseline exists yet (first run), performance_targets are NOT evaluated — run joins baseline cluster instead |
| **REQ-057** | **Environment fingerprint captured with each baseline.** Baseline bundle includes `fingerprint.json` with: daemon version + git commit, per-backend `/v1/models` response (captures vLLM version, model id, quantization), model weights SHA256 where available, `uname -a` output, CPU model from `/proc/cpuinfo` or `sysctl machdep.cpu.brand_string`, total RAM, GPU topology via `nvidia-smi topo -m` when GPUs are present, scheduling-mode flags (for vLLM: `VLLM_ENABLE_V1_MULTIPROCESSING`, `VLLM_USE_V2_MODEL_RUNNER`). When vLLM is in the fleet AND its CLI supports it, run `vllm collect-env --output vllm-fingerprint.json` and include in the bundle. Fingerprint hash = SHA256 of sorted JSON canonicalization of the above |
| **REQ-058** | **Baseline invalidation — fingerprint-first, TTL-fallback.** At gate run time, runner computes current environment fingerprint hash and compares against the stored baseline's hash. Mismatch → baseline is INVALID, gate run pre-flight fails with CONFIG_ERROR exit 6 naming which fingerprint dimensions differ (e.g. "vLLM version 0.18.1 → 0.19.0 changed since baseline"). Fallback TTL: `baseline_valid_until: <ISO date>` captured in baseline bundle (default 90 days from capture). Expired → same CONFIG_ERROR path. Override: `--re-baseline` flag re-runs the K-cluster capture with the current environment; `--override-stale-baseline` runs the gate against the old baseline with a WARN logged (escape hatch for "I know what I'm doing, this is close enough"). **ROUND 9 PHASE 3 BLOCKER B1 FIX (2026-04-23 twin-audited): cross-gate baseline snapshot-pinning for ΔF1 references.** When a gate declares cross-gate metrics (e.g., Gate 2's `delta_f1_vs_gate_1_5_baseline`, Gate 1b's F1 delta vs Gate 1, Gate 1.5's uplift vs max(Gate 1, Gate 1b)), the referenced baseline MUST be pinned to a specific cluster UUID via `baseline_reference_pin:` block in the gate YAML. Schema: `baseline_reference_pin: { source_gate: String, source_cluster_uuid: String, source_bundle_hash: String }` — `source_cluster_uuid` names the canonical Gate N cluster bundle whose baseline is the ΔF1 denominator; `source_bundle_hash` is the sha256 of that bundle's `manifest.json` at pin-time. Runner verifies at Gate N+1 load: (a) source cluster UUID exists at `~/.pantheon/evidence/gate-{source_gate}/cluster-{uuid}/`, (b) bundle hash matches — if source bundle has been modified since pinning (re-baselined, re-run, etc.), CONFIG_ERROR exit 6 with explicit message "baseline_reference_pin stale; Gate N+1 meaning would silently change — either update pin to current Gate N cluster or re-run Gate N+1 against intentional new baseline." This closes the twin-audited blocker where Gate 2 (ΔF1 vs Gate 1.5 serial baseline) would silently change meaning if Gate 1.5's YAML changed. Empty or missing pin block at Gate N+1 YAML load = CONFIG_ERROR exit 6 ("cross-gate ΔF1 declared without baseline_reference_pin — reproducibility impossible"). Pin block MUST be populated at gate-authoring time with the experimentally-appropriate source cluster; "pending first Gate N run" is a valid pin state only for pre-first-run gates, with the sentinel `source_cluster_uuid: PENDING_FIRST_RUN` and loader behavior permitting gate execution to pin the first Gate N cluster UUID at its post-completion bundle-write, but REFUSING subsequent runs until operator explicitly acknowledges the pin via `--acknowledge-baseline-pin <cluster-uuid>` CLI flag. Prevents the quiet-drift failure mode where operator re-runs Gate 1.5 post-Gate-2 and accidentally invalidates Gate 2's reproducibility without realizing. **ROUND 9 PHASE 3 BLOCKER B1 HARDENING (post-twin-audit 2026-04-23):** `--acknowledge-baseline-pin <cluster-uuid>` token is SINGLE-USE, persisted at `~/.pantheon/baseline/acknowledgments.jsonl` (append-only with ISO timestamp + cluster UUID + operator + reason-string from `--pin-ack-reason` required flag), and BLOCKED for any gate declaring `substrate_claim_bearing: true` in its YAML. Production-floor claim-bearing runs (Gate 1.5, Gate 2, future Gate 3) MUST have a fully-pinned baseline at gate YAML load — no acknowledge-token bypass permitted. Only bootstrap gates (Gate 1, Gate 1b at first-run) may use PENDING_FIRST_RUN + single-use acknowledge. Subsequent runs of a claim-bearing gate with stale pin → CONFIG_ERROR exit 6; no acknowledge-token escape. Rationale: twin audit identified the original fix's operator-acknowledge path as a loophole enabling repeated drift bypass. Hardening restricts bypass to one-time bootstrap only |
| **REQ-059** | **Gate 0 is composed of four sub-gates (Gate 0.1 / 0.2 / 0.3 / 0.4), each a staged-complexity ramp validating ONE Backend impl against ONE real downstream service.** Each sub-gate has its own YAML at `gates/gate-0.{1,2,3,4}.yaml`, its own baseline bundle, its own verdict. Sub-gates are sequential prerequisites: Gate 0.N+1 runner refuses to run if Gate 0.N has not achieved PASS or PASS_AFTER_RETRIES (bypass via `--skip-prerequisite-check` with WARN). Composition: **Gate 0.1** = `TriumvirateDaemon` backend → daemon's agent-adapter → Claude/Codex/Gemini CLI subprocess (no network beyond localhost), three hypotheses (one per CLI). **Gate 0.2** = `TriumvirateDaemon` backend → daemon's agent-adapter → commercial API (Anthropic / OpenAI / Google) using Tier 0 secrets, three hypotheses (one per provider). **Gate 0.3** = `HttpEndpoint` backend → MLX-lm server on Mac serving Qwen2.5-0.5B-Instruct (OpenAI-compat /v1/chat/completions, single-box, no LAN). **Gate 0.4** = `HttpEndpoint` backend → vLLM server on homebox serving Qwen2.5-0.5B-Instruct (OpenAI-compat /v1/chat/completions over LAN). Each sub-gate validates exactly one new variable beyond the prior sub-gate; failure isolates to that one delta. Shared prompt pool (REQ-061) across all four sub-gates for direct comparability |
| **REQ-060** | **Fleet YAML entry gains optional `role: String` field — Level 2 role semantics (metadata, not enforced).** Each fleet entry may declare `role:` separately from its dispatch-key name. The role string is free-form but should draw from a shared vocabulary (e.g. `dispatcher`, `coordinator`, `worker`, `reasoner`, `reviewer`, `critic`, `generator`, `summarizer`). Cumulative log (REQ-048) keys `by_role:` on the `role` field when present, falls back to dispatch-key when absent. Downstream analytics can then query "every coordinator-role run across any gate" — decoupling semantic purpose from arbitrary dispatch-key naming. Role is NOT enforced against capability requirements in v1 (Level 3 upgrade path reserved); downstream gates may declare required roles but cannot yet require specific capabilities per role |
| **REQ-061** | **Shared Gate 0 prompt pool at `gates/prompts/gate-0-pool.yaml`**, hand-authored (~100 prompts, constrained to Qwen2.5-0.5B-Instruct compatibility), used across all four Gate 0 sub-gates for direct cross-backend comparability. Each prompt is a record with: `prompt_id: Uuid` (UUIDv7, stable across runs), `text: String`, `tags: Vec<String>` (e.g. `["short", "factual", "code-generation", "unicode", "math", "refusal-likely"]`), `expected_difficulty: Enum { Low, Medium, High }`, `purpose: String` (one-line description of what this prompt exercises), `max_expected_output_tokens: Option<u32>`. `PromptRecord` carries `prompt_id` alongside `task_id`; cumulative log (REQ-048) additionally keys per-run results on `prompt_id` enabling the per-prompt cross-backend effectiveness atlas. Later gates author their own pools at `gates/prompts/gate-N-pool.yaml` (or reuse Gate 0's pool when appropriate); prompt_ids are globally stable so shared prompts across gates tie together in analytics |
| **REQ-062** | **Per-hypothesis `request_timeout_sec` with sub-gate defaults.** Sub-gate YAML declares `default_request_timeout_sec: N` at top level. Each hypothesis inherits this default but may override via its own `request_timeout_sec: N` in `scenario_config`. Recommended defaults (enforced as the value the sub-gate YAML ships with, but operator can override): Gate 0.1 CLI = 60s, Gate 0.2 API = 30s, Gate 0.3 MLX = 15s, Gate 0.4 vLLM = 15s. Higher gates authored over time set their own per-gate/per-hypothesis values matching observed backend behavior |
| **REQ-063** | **Explicit warmup before baseline cluster.** Each hypothesis in a sub-gate declares `warmup_requests: N` (default 2). Before the K=5 baseline cluster begins (REQ-054), runner fires N warmup requests against the same Backend with discarded results — warming subprocess caches (CLI), provider connection pools (API), model-memory caches (MLX/vLLM). Warmup metrics are NOT written to `metrics/` or `raw/prompt-records.jsonl`; a `manifest.json` entry records `warmup_completed: true, warmup_count: N, warmup_duration_ms: T` for audit. Warmup failures on ALL N attempts → abort sub-gate with specific CONFIG_ERROR (different exit code from cold-start pre-flight failures: exit 7 = WARMUP_FAILED) |
| **REQ-064** | **`expected_contains_any` — OR-match primitive alongside single-substring `expected_contains` (pool + overlay schema).** Prompt-pool entries and hypothesis-level `fingerprint_overlay` entries may specify `expected_contains_any: Vec<String>` as an alternative to `expected_contains: String`. Match semantics: response text contains AT LEAST ONE of the listed substrings (case-handled per `expected_case_sensitive` flag; default false). ## Architecture

### Backend + FleetOrchestrator trait layer

```rust
#[async_trait]
pub trait Backend: Send + Sync {
    async fn chat_completion(&self, req: ChatRequest) -> Result<ChatResponse, PromptError>;
    fn endpoint_label(&self) -> &str;
    fn capabilities(&self) -> BackendCapabilities;
}

pub struct HttpEndpoint {
    pub url: String,
    pub model: String,
    pub client: reqwest::Client,
    pub semaphore: Arc<Semaphore>,
}

pub struct TriumvirateDaemon {
    pub daemon_url: String,   // e.g. http://localhost:7788
    pub client: reqwest::Client,
    pub semaphore: Arc<Semaphore>,
}

pub struct FleetOrchestrator {
    pub roles: BTreeMap<String, Arc<dyn Backend>>,
    pub label: String,
}

#[async_trait]
impl Backend for FleetOrchestrator {
    async fn chat_completion(&self, req: ChatRequest) -> Result<ChatResponse, PromptError> {
        // Role routing per req.role (default "primary")
        let role = req.role.as_deref().unwrap_or("primary");
        let backend = self.roles.get(role)
            .ok_or_else(|| PromptError::config_missing_role(role))?;
        backend.chat_completion(req).await
    }
    fn capabilities(&self) -> BackendCapabilities {
        // Intersection across members
        self.roles.values().map(|b| b.capabilities()).reduce(|acc, c| acc.intersect(&c)).unwrap_or_default()
    }
    fn endpoint_label(&self) -> &str { &self.label }
}
```

A fleet of 1 is constructed by putting one Backend in `roles` under `"primary"`. Scenarios never special-case.

## Scenario Semantics

| Scenario | Behavior |
|---|---|
| `task-dispatch-smoke` | Sequential N requests against a Backend (or fleet role). Median + mean latency, tasks_completed, tasks_errored. PASS per targets |
| `throughput-sustained` | N concurrent streams for duration; each stream loops back-to-back requests. Records tok/s per stream + aggregate, p50/p95/p99 latency via `hdrhistogram`, error rate |
| `multi-endpoint-concurrent` | Runs `throughput-sustained` against ≥2 roles of a FleetOrchestrator in parallel. Each role gets its own stream count. Aggregate verdict per role; overall PASS if all roles PASS |
